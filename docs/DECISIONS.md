## ADR-001：视觉基调采用「暖矿物卡其 + 酸黄点睛」，而非科技冷青

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：需求要求视觉对齐《明日方舟》「莱茵生命 (Rhine Lab)」的平面设计。直觉上「科研机构 / 3D 赛博」应当是冷青蓝，最初实现也押注了高饱和冷青 `#3fd4c8`。但这与「莱茵生命」到底是否对味，缺乏证据。
- **考虑过的方案**：
  - A. 沿用直觉的「科技冷青」基调。
  - B. 对莱茵生命官方物料做程序化取色，用实测数据决定基调。
- **决策**：采用 B。对莱茵生命一手物料（6 张游戏内场景背景 + 4 张官方壁纸 + 5 张干员立绘 + logo）做程序化取色，结论与直觉相反：
  - 莱茵生命的**环境 / 材质 / 立绘是暖橄榄·卡其·米白 + 暖黄灯带**，实测饱和度仅 5–24%（例：塞雷娅的「黑」实为 `#383028` 暖黑，非冷黑）。设定上 RL 位于哥伦比亚 Trimounts（MIT 影射）的理工校区 + 军工科研所，解释了暖木 / 卡其 / 军绿的室内调性。
  - 只有 RL 的**平面标识系统**（logo、电路板底纹）是深蓝黑 + 冷白细线。
  - 明日方舟标志酸黄经一手查证为 `#FDF900`（取自鹰角官网活动配置的 `themeColor`）。
  - 最终基调：「**暗底取冷、主体取暖、点睛用酸黄**」——晶格主体暖矿物卡其 `#b8a878`、波谷偏橄榄、暗场暖近黑 `#0b0a07`、波峰尖点酸黄 `#FDF900`、冷青 `#5f8a94` 降级为仪器轮廓光。暖 70% / 冷 30% 并存。
- **为什么选这个**：有实测证据支撑，「对味」而非「泛泛科技感」；这是作品与套模板的分水岭。
- **为什么不选其他**：方案 A 纯属臆测，且饱和度 ≈70% 的冷青违反 RL 物料「低饱和（5–24%）」的硬特征。
- **后果**：确立硬约束——**不出现任何饱和度 >40% 的大面积色块**；配色全部收敛到 `palette.ts`（见 ADR-003）。完整取证与所有精确 hex 见 `src/theme/palette.ts` 注释。
- **何时重新审视**：若要切换到其他阵营 / 世界观的视觉参照时。

## ADR-002：工具链采用 Vite+（`vp` CLI）

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：需求指定用 viteplus + React 19.3 构建纯前端页面。
- **决策**：使用 `vite-plus@1.0.0`（`vp` CLI）脚手架 `create-vite` 的 react-ts 模板；`vite` 经 pnpm catalog 锁到 `@voidzero-dev/vite-plus-core@1.0.0`。
- **为什么选这个**：满足需求指定；Vite+ 统一了 Vite/Rolldown/Vitest/Oxlint/Oxfmt，配置集中在 `vite.config.ts` 的 `defineConfig`（含 lint 规则），减少工具碎片。
- **后果**：`vp dev/build/lint` 为内置命令；项目脚本经 `vp run` / `vpr`。React 精确锁 19.3.0（`@react-three/fiber` peer 要求 `>=19 <19.4`）。
- **何时重新审视**：Vite+ 有破坏性更新，或需迁回标准 Vite 时。

## ADR-003：配色 / 文案 / 动画速度三大单一真相源

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：视觉作品需要频繁微调，若颜色 hex、文案、动画时长散落在各组件里，维护成本会迅速失控。
- **决策**：建立三个横切令牌系统，改任一类只动一个文件：
  - **配色** `theme/palette.ts`：3D 侧直接 import；HUD 侧经 `injectPalette()` 写入 `:root` 的 `--c-*` CSS 变量。
  - **文案** `i18n/messages.ts`：扁平点分 key 词条表，组件经类型安全的 `t(key, vars)` 取值（key 用模板字面量类型约束，拼错即编译报错）。
  - **动画速度** `theme/motion.ts`：`UI_TIME_SCALE`（时长倍率）经 `injectMotion()` 写成 CSS `--motion`，所有时长用 `calc(基准 × var(--motion))`；`SCENE_SPEED`（频率倍率）供 3D 用 `elapsedTime × SCENE_SPEED` 作统一时间基。
- **为什么选这个**：一处修改、全站同步；令牌与消费方解耦，改视觉不必理解 3D 或组件细节。
- **后果**：组件内**禁止硬编码** hex / 显示文本 / 动画 ms；`content.ts` 只留结构数据（id/status/href），与文案分离。
- **何时重新审视**：出现第四类需要全站统一的横切关注点时，可沿用同一模式。

## ADR-004：文案管制用自研极简 i18n，不引运行时库

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：需求要求「所有字符串进入 i18n 管制，不区分语言，只为方便改字符串」。
- **考虑过的方案**：A. 引入 i18next / react-intl 等成熟库；B. 自研 `t()` + 词条表。
- **决策**：采用 B。一个 `messages.ts` 常量表 + 一个 `t(key, vars)` 函数，无运行时依赖、无 Provider、无 locale 状态。
- **为什么选这个**：需求明确「不区分语言」，成熟库的 locale 切换 / 复数 / 插值引擎是过度设计；自研方案类型安全（key 编译期校验）、零依赖、零学习成本。
- **为什么不选其他**：i18next 等会引入运行时体积与 Provider 样板，而当前用不到其核心能力。
- **后果**：这是「文案集中管理」而非「国际化」。将来要多语言，把 catalog 改为 `{ [locale]: ... }` 并让 `t()` 按 locale 取值即可，**key 与调用方不变**。
- **何时重新审视**：真正需要多语言切换 / 复数规则 / 日期本地化时。

## ADR-005：色调映射全场景只做一次（后处理链内的 ACES）

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：r3f 默认给渲染器开 `ACESFilmicToneMapping`，而后处理链里也有一个 `ToneMapping` effect。两者叠加会对同一画面应用两次 ACES，导致暗部发灰、高光死白。
- **决策**：Canvas 的 `gl.toneMapping` 设为 `THREE.NoToneMapping`，色调映射统一交给后处理链里的那一次；自定义 shader 材质设 `toneMapped={false}`（自行管理色彩空间）。
- **后果**：这是必须守住的技术边界——任何给渲染器再开 tonemapping 的改动都会重新引入双重映射。
- **何时重新审视**：更换后处理方案或渲染管线时。

## ADR-006：开机引导序列纯时间驱动，绝不无限等待场景就绪

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：早期实现让引导幕死等 `sceneReady`（3D 首帧信号）。但软件渲染 / 低端机下首帧可能要数秒，导致用户长时间面对黑场。
- **决策**：相位推进（LOADING→SCAN→REVEAL→IDLE）完全由时间驱动；`sceneReady` 只用于「提前加速」，另有 `MAX_LOADING` 硬性兜底强制开演。
- **为什么选这个**：入场体验不应被最慢的渲染路径绑架；宁可场景稍后就位，也不让用户干等。
- **后果**：引导幕停留时间可预期（受 `motion.ts` 的 BOOT 时序控制）；`reducedMotion` 偏好下直接落到 IDLE，跳过全部引导动画。
- **何时重新审视**：若引入真实异步资源加载（外部模型/贴图）需要精确进度时。

## ADR-007：3D 随机性用种子化 PRNG（mulberry32），不用 Math.random

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：晶格 / 微粒的初始相位需要随机分布。React Compiler 的纯度规则正确地指出渲染期间调 `Math.random` 不纯；且生成艺术作品需要可复现性。
- **决策**：`scene/prng.ts` 提供 `mulberry32(seed)`，各处用固定种子生成随机相位。
- **为什么选这个**：既满足 React 纯度，又让「同一颗种子永远长出同一片晶格」——利于调试与视觉一致性。
- **后果**：随机分布可复现；换种子即换一种晶格形态。
- **何时重新审视**：需要真正的运行时不可预测随机（如用户驱动的生成）时。

## ADR-008：字体经 @fontsource 打进 bundle，零外链

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：鹰角式美学依赖 condensed 显示体（Oswald）与等宽数据体（JetBrains Mono）。用 Google Fonts 外链在国内访问不稳定。
- **决策**：用 `@fontsource` 把 woff2 作为依赖打进 bundle，运行时零外部请求；中文回退到系统字体栈（PingFang SC / Microsoft YaHei）。
- **为什么选这个**：国内访问可靠、无第三方运行时依赖、加载可预测。
- **后果**：bundle 略增（字体 woff2）；不引入体积大的中文字体全字重，靠系统字体兜底。
- **何时重新审视**：需要特定中文 webfont 且能接受其体积 / 子集化成本时。

## ADR-009：页面品牌与内部设计参照分离

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：项目最初把内部设计 DNA 直接搬上了页面文案——顶栏 `RHODES ISLAND`、眉标「莱茵生命」、遥测标签 `SHM · y=A·sin(ωt+φ)`、项目描述里的 `Three.js`、主标题 `HARMONIC LATTICE`。但这是**对外的演示项目门户**，访客不需要、也不应该看到底层参照的世界观名词、物理术语和实现技术；这些暴露既显得未打磨，也把「致敬」与「原创品牌」混为一谈。
- **考虑过的方案**：
  - A. 页面继续外露这些概念（保持「设计过程的透明」）。
  - B. 页面只呈现 XRL 自有品牌，内部参照退回代码注释与 `docs/`。
- **决策**：采用 B。确立一条硬边界：
  - **页面可见文案**只呈现 XRL 品牌（顶栏 `XRL DEMONSTRATION`、主标题 `THINK DIFFERENT`）与作品名。
  - **不得出现在页面**：世界观名词（莱茵生命 / 罗德岛）、视觉母题术语（简谐运动 / SHM 公式）、渲染库名（Three.js / r3f）。
  - **允许出现在**：代码注释、`docs/`（ADR、ARCHITECTURE、specs）、组件与文件名（如 `HarmonicLattice.tsx`）——即内部层。
  - 主标题下引言取自 1997 Apple「Think Different」广告并如实署名 `— Steve Jobs, 1997`，在 README 授权段声明版权归属。
- **为什么选这个**：对外门户要的是「成品感」与清晰的品牌归属；内部参照是实现细节，属于工程文档而非产品界面。分层后，页面干净、内部知识也没丢。
- **为什么不选其他**：方案 A 会让页面像「半成品 + 致敬拼贴」，且混淆原创与参照的界限。
- **后果**：
  - 视觉母题（简谐行波）、光影取证（莱茵生命暖矿物）、组件名**保持不变**——只改「说什么」，不改「做成什么样」。
  - 三个占位子项目（GLASS PROTOCOL / SIGNAL DRIFT / TERMINAL 404）换成四个**真实作品**（赛博拼豆 / 车牌生成 / 音乐播放器 / 富文本记事），编号 `OP-*` → `PRJ-*`，`href` 从空改为真实路径，点击**新开标签页**（见 ADR-010）。
  - 项目顺序即展示优先级：赛博拼豆排 PRJ-01。改序需**同步两处**——`content.ts` 的 `projects` 数组顺序 + `messages.ts` 的 `PRJ` 编号（二者数据源不同，靠注释提醒）。
  - 此边界写进 `AGENTS.md` 全局规则，约束后续所有文案改动。
- **何时重新审视**：若门户定位从「对外作品展示」转为「设计过程透明化 / 教学」时。

## ADR-010：子项目入口新开标签页，而非当前页路由跳转

- **日期**：2026-10-02
- **状态**：已采纳
- **背景**：四个作品是部署在同域名下不同路径的独立子站。默认 `<a href>` 会在当前页跳转，访客离开门户后需手动返回。
- **决策**：导航链接加 `target="_blank" rel="noopener noreferrer"`，点击在新标签页打开子站，门户常驻原标签页。
- **为什么选这个**：门户是「入口」，应始终保持可达；新开页符合「作品集首页」的浏览心智。`noopener` 防子站经 `window.opener` 反向操控门户（安全），`noreferrer` 不外泄来源（隐私）。
- **后果**：`ProjectNav.tsx` 对有 `href` 的条目渲染带上述属性的 `<a>`；无 `href` 时降级为不可点的 `<span>`（当前四项都有真实链接）。
- **何时重新审视**：若改为把子站作为本站内路由页面（同一 SPA）承载时。
